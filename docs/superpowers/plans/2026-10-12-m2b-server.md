# Milestone 2b: Game Server (Host with Mobile Players) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A server process that hosts TripleA games on the desktop engine. Human seats are played
from phones over WebSocket/JSON (`protocol/`, `online/` from milestone 2a). It has accounts, keeps
every running game in Postgres and resumes it after a restart. Test: two scripted phone clients play
the minimap against the AI over real WebSockets, across a server restart.

**Architecture:**
- New repo folder `C:\dev\triplea-game.github.io\triplea-mobile-server`, next to this repo.
  - `triplea/` is a clone of the desktop repo at tag `2026-10.16.15815`. It already exists; do not
    modify it. It is used as a Gradle composite build (`includeBuild("triplea")`).
  - The mobile repo is read from `../triplea-mobile`: Gradle property `mobileDir`, default
    `../triplea-mobile`.
  - One Gradle module `server` (Kotlin/JVM, Java 25).
- `server` compiles three source sets from the mobile repo against the desktop engine:
  - `protocol/src/main/kotlin`;
  - `online/src/main/kotlin`;
  - the mobile engine files `GameEventListener`, `HumanPlayerUi`, `MobilePlayer`, `PlayerKind`,
    `MobileSoundChannel` and `MobileDisplay` (from `engine/src/main/java/org/triplea/mobile/`).
- Layers inside `server`:
  - `HostedGame`: one `ServerGame` per game on its own thread, built like
    `LocalGameSession.create`.
  - `GameService`: creates, persists, resumes and lists games.
  - `Db`: Postgres through JDBC, HikariCP and Flyway.

## Global Constraints

- **No git operations.** No `git commit`, `git push` or `git add` in either repo. Do not run
  `git init` in the server folder; the README tells the user how to make it a repo with submodules.
  Leave all changes in the working tree.
- **`triplea/` (desktop clone) and `C:\dev\triplea-game.github.io\triplea` are read-only.** Building
  `triplea/` through the composite build (which writes its `build/` folders) is allowed.
- **Mobile repo rules:**
  - Files under `engine/src` and `app/src` are edited with Edit/Write only, never with shell tools.
  - `./gradlew` (in either repo) needs the `build` skill loaded first.
  - The server's Gradle must run on JDK 25:
    `JAVA_HOME="/c/Users/Windows 11/.jdks/jbr-25.0.2"` (Git Bash path), or let the toolchain
    auto-detect it.
- **Secrets:** none in files that would be committed. Configuration comes from environment
  variables; `.env` is gitignored, and `.env.example` documents the variables.
- **Only load saves the server wrote itself.** Clients never upload save bytes.
- **Protocol and size limits:**
  - JSON messages only on the app path, through `ProtocolJson`; 64 KB per message.
  - The WebSocket frame limit is set in Ktor (`maxFrameSize = 64 * 1024`), so oversized frames are
    refused before they are buffered. This closes a parked 2a finding.
  - Saves larger than 10 MB are refused on download (spec).
- **Answers:** an `Answer` must come from the user who owns the seat of the open question, and
  match its id. Anything else is ignored and logged; a mismatched id gets `Rejected`.
- **Edit mode is always off.** No edit delegate is reachable from the app path; the protocol has
  no edit messages.
- **Every new non-trivial piece has a test.** Server tests use Testcontainers Postgres
  (`postgres:17-alpine`).
- **Don't change the mobile repo, except:**
  - `MobileDisplay.java`: drop the `@Override` on `unitsMoved` (Task 1);
  - `protocol/` REST types (Task 3);
  - `docs/DEVELOPMENT.md` (Task 5).

## Review Focus

1. **Server restart while a question is open.** After the restart the same seat must be asked
   again, and the reconnecting phone must get `GameVersion` and the question again. Test in Task 4.
2. **Two connections of the same user** (phone and emulator). Both get the question, the first
   valid answer wins, and the second gets `Rejected` ("question already answered"). Test in Task 4.
3. **An answer from a user who does not own the seat, or for an old question id**, must never reach
   the engine. Test in Task 4.
4. **The game thread must never block the WebSocket threads, and the reverse.**
   - Sending a message to a slow or dead connection must not stall the game.
   - A game thread waiting for an answer must not hold the data read lock (the save needs the
     write lock).
5. **Game end:** the winner is stored, the status becomes `finished`, every participant gets
   `Event.GameEnded`, and the game thread exits. Test in Task 4.

create table users (
  id bigserial primary key,

  password_hash text not null,
  created_at timestamptz not null default now()
);

  map_name text not null,
  game_name text not null,

  created_at timestamptz not null default now(),

);
create table seats (
  game_id text not null references games on delete cascade,

**Routes:**
- `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh` return `TokensDto`. Failures
  return 400 or 401 with `ErrorDto`.
- Everything below needs `Authorization: Bearer <access token>`; without it the answer is 401.
- `GET /maps` returns `List<MapGameDto>` from `Engine.installedGames()`.
- `POST /games` creates a game from `CreateGameRequest` and returns `GameInfoDto`. Validation:
  - the game exists;
  - every nation of the game has exactly one seat and there are no unknown nations;
  - HUMAN seats name existing users;
  - the creator holds at least one HUMAN seat;
  - otherwise 400 with the reason.
- `GET /games` returns the caller's games (they hold a seat), running first.
- `GET /games/{id}` returns one game. The caller must hold a seat, else 404.
- `GET /games/{id}/save` returns the latest snapshot bytes:
  - `Content-Type: application/octet-stream` and header `X-Game-Version: <version>`;
  - the caller must hold a seat, else 404;
  - more than 10 MB gives 500 and a log line.

**`/ws` protocol:**
1. Authentication:
   - The client opens `/ws` with `Authorization: Bearer <access token>`.
   - Without a valid token the server closes with code 4401 (`VIOLATED_POLICY` is fine if custom
     codes are awkward). Expired tokens fail the same way.
2. The first frame must be `Hello`:
   - incompatible: send `UpdateRequired(PROTOCOL_VERSION, ENGINE_BASE_TAG)` and close;
   - any other first frame: close.
3. After `Hello`, for every running game the user holds a seat in:
   - send `GameVersion(gameId, version)`;
   - if that game has an open question for one of the user's seats, send that `Question` again.
4. Client frames:
   - `Answer`:
     - unknown question id, or the id is not the open question of a game where this user owns the
       question's seat: `Rejected(id, "not your question")` or `Rejected(id, "question already
       answered")`;
     - otherwise the waiting game thread is completed with it. Only the first valid answer counts.
   - `PlaceableQuery`: the same ownership check; the answer comes from
     `answerPlaceable(query, game.data, game.delegates)` and is sent back.
   - A frame that does not decode (bad JSON, too large): close the connection with a reason and
     log it.
5. Size limits: Ktor `maxFrameSize = 64 * 1024`, plus `ProtocolJson` decode limits.

**`GameLink` (game thread side, `HostLink` per game):**
- `ask(seat, ask)`:
  1. `version = gameService.snapshot(gameId)` (the save is taken while this game thread waits);
  2. flush the queued events of this game to all participants as `GameEvent(gameId, version, e)`;
  3. send `GameVersion(gameId, version)` to all participants;
  4. create a `Question(id = nextId(), gameId, seat, version, ask)`, remember it as the game's
     open question and send it to every connection of the seat owner;
  5. block on a `CompletableFuture<Answer>`.

  When the game is stopped, the wait ends with `GameOverException`.
- Question ids come from a process-wide `AtomicLong`, seeded with `System.currentTimeMillis() * 1000`,
  so they are unique across restarts.
- `reject(questionId, reason)` sends `Rejected` to the seat owner.
- `notify(seat, note)` flushes events, then sends `Notice(gameId, seat, currentVersion, note)` to the
  seat owner.
- Events (`EventEncoder` → `GameLink`):
  - They are queued per game and flushed at the next `ask`, `notify` and game end. The device copy
    is synced to the snapshot of that version, so it knows every unit in the events.
  - `Event.GameEnded` is queued by `onEnd` and flushed after the final snapshot.
- Sending never blocks the game thread:
  - each connection has a bounded queue (e.g. a `Channel(256)`);
  - when it overflows, that connection is closed (the client reconnects and resyncs).

**Disconnect and restart:**
- A disconnect only removes the connection. The open question stays and is re-sent on the next
  `Hello`.
- On restart, `resumeAll` re-runs every running game from its snapshot. The engine asks the same
  step again (research section 3), which creates a new question id.
